# F-Droid

`org.fastpool.signerguide.yml` is copied verbatim into [fdroiddata][] as
`metadata/org.fastpool.signerguide.yml`. It carries no comments because
fdroiddata's CI runs `fdroid rewritemeta` and fails on any diff — the canonical
form is the only form it accepts. The reasoning lives here instead.

[fdroiddata]: https://gitlab.com/fdroid/fdroiddata

## What F-Droid actually does

It builds from source, on its own machines, and signs with its own key. The APK
on F-Droid is therefore **not** the APK on Zapstore or Play: same code,
different signature, and Android will not upgrade one into the other. That is
normal and expected across stores.

The listing does not come from the merge request either. F-Droid reads
`fastlane/metadata/android/<locale>/` out of *this* repository at the tagged
commit, which is why that tree is generated — `node scripts/make-fdroid-metadata.mjs`,
from the same copy the Play listing uses — and committed.

## The four things that were not obvious

**1. `android/` has to be committed.** `fdroidserver` checks that `subdir`
exists and raises `Missing subdir` *before* it runs `init` or `prebuild`
(`common.py`, `prepare_source`). So `expo prebuild` cannot generate the Gradle
project during the build — it does not get the chance. The alternative, dropping
`subdir` and driving `./gradlew` from a raw `build:` step, does not work either:
the scanner deletes `gradlew` and `gradle-wrapper.jar` on sight, and F-Droid
builds with its own `gradlew-fdroid`.

Committing it is also the better answer on the merits. `npx expo prebuild` at
build time would hand F-Droid a native project generated by whatever Expo
resolved to that day, which is the opposite of a reproducible build.

The cost is that `app.json` is no longer the only place the manifest, the icons
and the version live. `npm run prebuild:check` regenerates `android/` from
scratch and fails on any drift. Run it before tagging.

**2. The listing goes at the top of the repository, not in `mobile/`.**
F-Droid accepts the fastlane tree in exactly three places (`update.py`, the
`found_in_subdir` test): the repository root, `<subdir>/`, or under a Gradle
flavour. Our `subdir` is `mobile/android`, so `mobile/fastlane` is none of the
three — it is skipped in silence, and the app publishes with no description and
no screenshots with nothing to say why. `mobile/android/fastlane` would satisfy
the rule but `expo prebuild --clean` deletes that directory wholesale.

**3. `node_modules` needs `scanignore`, not `scandelete`.** The scan runs
between `prebuild` and the build (`build.py`: `prepare_source` at 507,
`scan_source` at 595), and Gradle shells out to node for the JS bundle. Deleting
the modules after installing them breaks the build that needs them.

**4. `Money` is not a category.** F-Droid has 108 and that is not one of them.
`Wallet` is where the crypto apps are — Bitcoin Wallet and Status both sit
there — and where someone looking for this would look, even though the app
holds no keys itself.

## AntiFeatures

`NonFreeNet` is declared rather than left to be discovered: the app talks to a
Stacks node (Hiro's by default, replaceable with `EXPO_PUBLIC_STACKS_API_URL`)
and a WalletConnect relay (Reown's). Neither is published as software.

It is deliberately **not** `Tracking`: no analytics, no advertising identifier,
no crash reporter. See `../privacy-policy.md` and `../data-safety.md`.

## Verifying before you submit

`fdroid lint` and `fdroid rewritemeta` can be run without their build
infrastructure:

```bash
python3 -m venv /tmp/fdvenv && /tmp/fdvenv/bin/pip install fdroidserver
git clone --depth 1 https://gitlab.com/fdroid/fdroiddata.git
cd fdroiddata
cp ../signer-guide/mobile/store/fdroid/org.fastpool.signerguide.yml metadata/
/tmp/fdvenv/bin/fdroid lint org.fastpool.signerguide     # must be silent
/tmp/fdvenv/bin/fdroid rewritemeta org.fastpool.signerguide
git diff --exit-code metadata/                            # must be empty
```

Both pass as of this writing.

What has **not** been done is `fdroid build org.fastpool.signerguide:1`, which
needs their buildserver VM (Debian, ~40GB, `vagrant up`). Everything above was
established by reading `fdroidserver` rather than by watching a build succeed,
so treat the first CI run on the merge request as the real test.

## Submitting

fdroiddata is on GitLab and takes merge requests, not GitHub pull requests.

1. Sign in at <https://gitlab.com> and fork
   <https://gitlab.com/fdroid/fdroiddata>.
2. ```bash
   git clone git@gitlab.com:<you>/fdroiddata.git
   cd fdroiddata
   git checkout -b signer-guide
   cp ../signer-guide/mobile/store/fdroid/org.fastpool.signerguide.yml metadata/
   git add metadata/org.fastpool.signerguide.yml
   git commit -m "New app: Signer Guide"
   git push -u origin signer-guide
   ```
3. Open the merge request against `fdroid/fdroiddata` `master`. Their CI runs
   lint and a build.

Expect review. The likely questions are the `scanignore` on `node_modules`
(answer: point 3 above) and the committed `android/` (point 1). Both are common
for React Native apps; Status is the precedent for the shape of this recipe.
